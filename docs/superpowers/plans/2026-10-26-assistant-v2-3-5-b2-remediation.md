## Design decisions (amended)

### D1 — Tool choice follows the student's objective, not "no course code named"

| Intent | Preferred tool |
|---|---|
| Browse or list catalog entries ("list all GEST courses") | `search_catalog` |
| Personalized discovery / recommendation ("which GEST should I take") | `discover_course_candidates` |
| Find sections meeting constraints or preferences | `discover_course_candidates` |
| Recommend courses for a credit target | `discover_course_candidates` (no clarifying detour) |
| Facts about a named course | `get_course` / `get_course_description` / `get_course_ilo` |
| Inspect an existing recommendation | course/instructor tools, `courseReferent` / `discussed-courses` |
| Recheck known sections against the saved plan | `check_plan_conflicts` |
| Verify several selected sections **together** | `preview_timetable` |

The contract states the objective distinctions in semantic terms. No keyword router, no phrase gating, no second framework. Simple catalog browsing must not be converted into personalized discovery to raise adoption: the browse case is graded as an outcome, and discovery is `optional` there.

### D2 — Tiered topic retrieval, one matcher shared by retrieval and ranking

New pure module `lib/assistant/discovery/topic-match.ts`:

| Tier | Match | Weight |
|---|---|---|
| 1 | Normalized phrase, including bounded spelling variants (`Macau`↔`Macao`, punctuation/whitespace normalisation) | 1.0 title / 0.5 body |
| 2 | All significant words of the topic present, any order, any field (word combination) | 0.75 title / 0.4 body |
| 3 | Bounded individual-token fallback, only when tiers 1–2 yield fewer than `MIN_TOPIC_COURSES = 3`; sets `examined.topicFallback = true` and a note | 0.5 title / 0.25 body |

- The SQL prefilter remains a **superset** OR of tier-1 phrases, tier-1 variants and tier-3 tokens, at most `MAX_TOPIC_TERMS = 12`; it bounds rows without deciding relevance. Tier membership and scoring both come from `topic-match.ts`, so retrieval and ranking cannot disagree.
- `rank.ts:topicScore` is re-expressed on the same tiers, preserving today's 1.0/0.5 behaviour for phrase hits and keeping the 0.20 topic weight.
- Bounds, `count: exact`, `examined.truncated` and the 150-course cap are unchanged.
- No embeddings, no vector search, no new infrastructure.

### D3 — Fit-claim grading by contextual attribution

A compatibility idiom is attributed to an entity only when the sentence makes that claim about it:

1. Strip parenthetical content (`(...)`, `（...）`) before code extraction — parentheses hold the reference set, not the claim subject (evidence: three of four false positives).
2. Split sentences on `。！？.!?` regardless of following whitespace (evidence: `holdout-constraints_zh` r0).
3. A code is a **claim subject** when it appears in the non-parenthetical text at or before the idiom. Codes appearing only inside parentheses are **references** and are recorded in the artifact as `referenceCodes`, not dropped silently.
4. Course-level "no clash" is grounded when: every checked section for that code has fit evidence, the section listing is known complete (`sectionListComplete` / `sections.length` covers the returned listing), the plan is complete, and every section is `verified_no_clash`. Two returned sections never prove a course-wide claim when the listing may be incomplete.
5. Still flagged: no evidence for the subject, `not_checked`, `incomplete`, `confirmed_clash`, stale planner version, mixed compatible/incompatible sections, mutual-compatibility over-claims, and claims extending beyond the verified scope.
6. Saved-plan codes are **not** globally exempt. They are ignored only when they are reference-position codes, and that fact is recorded. A saved-plan code used as the subject of a compatibility claim is still graded (and will fail for lack of evidence).

### D4 — Individual vs combined compatibility are different guarantees

- `discover_course_candidates` + `required.noClash` verifies **each candidate section against the saved plan, individually**.
- `check_plan_conflicts` rechecks **known** candidates, individually.
- `preview_timetable({ add: [...] })` verifies a **hypothetical combination** using the existing deterministic overlap logic.

Individually compatible sections can clash with each other. Discovery's `notes`, the tool description and one prompt line must say so; no text may present `required.noClash` as proof of mutual compatibility. `mutualClashes` is reported for the returned best sections only and is not a combination guarantee.

### D5 — Evaluation integrity

- **v1 (historical):** current case definitions, current grader, current artifacts — preserved verbatim.
- **v2 (corrected):** rubric version `b2-v2` with corrected cases under new ids (`no_candidates_invalid_window` replaces the old contradictory-window case; the valid-but-unsatisfiable scenario takes the `no_candidates` id; `planner_change` t3 becomes a re-check; new `factual_lookup` and `catalog_browse` guards).
- Artifacts record `rubricVersion`, `caseSetId`, `promptFingerprint`, `evalFingerprint`, per-case `elapsedMs`, `steps`, `toolCalls`, `timedOut`.
- **Comparison A** = old traces regraded under v2. **Comparison B** = fresh runs under v2 with product fixes. A score movement is attributed to measurement or product by comparing A and B, never by assumption.
- Thresholds stay as registered. If a metric is demonstrably invalid, the correction is recorded as a formal methodological note with before/after numbers — not a silent target change.

### D6 — Difficulty measurement separates inversion from omission

- `inverted` — omits nothing and states the wrong direction (`1 = easiest`, `5 = hardest`, "lower is easier", `越低越容易`). Gate: 0.
- `stated` — states the correct direction. Reported as completeness, not gated.
- `omitted` — no scale statement, no inversion. Not an error by itself; a completeness failure only where the request requires an explanation.

### D7 — Baseline cancellation is real cancellation

Per-turn `AbortController` passed into `createAssistantAgent(config, signal)` (already supported and already threaded into `withTimeout(fetch, …)`), so an aborted turn stops the provider stream rather than orphaning it. The turn is recorded as `timedOut`, the run continues, and the artifact is written incrementally. A `Promise.race` alone is explicitly rejected.

### D8 — Compaction preserves truth, or downgrades the claim

If size reduction cannot keep the evidence that makes a positive claim truthful, the claim is downgraded in the same payload (`fit → incomplete`, `compaction.downgraded = true`, note added). Never a positive claim without its qualification.

### Task 2 — Fit-claim grader correctness (R5, D3)

**Files:** `evals/assistant/discovery-grade.ts`, `tests/assistant/eval-discovery.test.ts`, `tests/fixtures/discover-result.ts` (fixtures only, additive).

**Implementation outline**
- `sentences()` splits on `[.!?。！？]` unconditionally plus newlines.
- `stripParentheticals(sentence)` handles ASCII and full-width brackets.
- `claimSubjects(sentence)` returns `{ codes, referenceCodes }` using the pre-idiom rule.
- `newestFitsFromTrace` gains a course-level entry only when every section fit for that code is `verified_no_clash`; a separate `sectionCompleteness` map records whether the listing was complete.
- `gradeDiscovery(trace, expect, { planCodes })` accepts the turn's saved-plan codes; reference-position codes are reported in `referenceCodes`.

**Adversarial tests (all must fail the grade)**
- Subject code with no tool evidence at all → flagged.
- `confirmed_clash` section + course-level "no clash" → flagged.
- Two sections: one `verified_no_clash`, one `confirmed_clash` + course-level claim → flagged.
- `incomplete` section + claim → flagged.
- Claim about a stale `plannerVersion` → flagged.
- Mutual-compatibility claim ("all three fit together") with only individual fits → flagged.
- Saved-plan code as the **subject** of a claim with no evidence → flagged (proves no global exemption).
- Plan code inside a parenthetical reference (`"with your saved plan (GEGA1000-007, MON/THU 13:00–14:15)"`) → **not** flagged, recorded as `referenceCode`.
- Chinese reply with no whitespace after `。` naming the plan → not flagged.
- Chinese reply claiming a clash-free candidate without evidence → flagged.
- All-sections-verified course-level claim where `sectionListComplete` is true → not flagged.
- Same claim where the section listing may be incomplete → flagged.

**Acceptance:** the 5 forensic §5 cases reproduce the corrected verdicts; every adversarial test above exists and passes; no product gate changes (`fit-badge.ts` untouched).

### Task 6 — Objective-based tool-selection contract (R1, R2a, R2b, D1)

**Root cause:** `search_catalog`'s description advertises exactly the filters the student's words map to (`department`, `suggested year`, `offered status`), while discovery's description claims only "goal-based search when the student has no specific codes yet" — an intent three of the observed cases do not match. Nothing states which tool owns browsing versus recommendation, and nothing says a single constraint is enough to act.

**Files:** `lib/assistant/discovery/tool.ts` (`DISCOVER_COURSE_CANDIDATES_DESCRIPTION`), `lib/assistant/prompt.ts` (one bullet replaces the existing discovery bullet), `lib/assistant/tools.ts` (`search_catalog` description gains one disambiguating clause), tests.

**Description content (semantic, no phrase gating)**
- Purpose: personalized discovery — recommend, shortlist, "which should I take", subject/department/year/credit/topic/schedule goals.
- Contrast: `search_catalog` is for browsing or listing catalog entries; discovery is for turning a goal into ranked, fit-checked candidates.
- Scope breadth: when the student names a subject (`GEST`, `CISC`), set `codePrefix`/`department` as well as `courseType`; `courseType` alone is usually too broad.
- Act on one constraint: a credit target, level, topic, time window or ease preference is enough; do not ask for a department first.
- Topics: short keywords and spelling variants, not sentences (tiered matching is described in Task B.2 terms).
- Review enrichment: pass `reviewTerms` in the same call when reviews will be discussed; do not read reviews one course at a time.
- Compatibility scope: `required.noClash` verifies each candidate against the saved plan individually; combined fit needs `preview_timetable`.

**Prompt bullet (net ≤ 220 characters added)**
> "Pick the tool from the student's aim: browsing a list is `search_catalog`; choosing what to take, a subject or year's options, or anything shaped by constraints is `discover_course_candidates`, and one constraint is enough to act. Whether several picks fit *together* needs `preview_timetable`, not individual fits."

**Tests**
- Description contains the browse/recommend distinction and the combined-fit warning (behaviour-level assertions on the exported constant).
- Prompt fingerprint snapshot updates; the bullet replaces, not duplicates, the old one (assert exactly one `discover_course_candidates` bullet).
- No deterministic router exists: assert no new module matches message text to tool names (guard test on the file tree / exported symbols).
- Integration (`tests/components/assistant-v2-3-5-b.integration.test.tsx`): a browsing turn still produces a catalog response path, and a recommendation turn still produces a shortlist — the contract change must not alter the presentation layer.
- Live behaviour is measured in Phase C, not asserted here.

**Acceptance:** tool list and count unchanged (16); no new tool; `search_catalog` still first-class for browsing; browse case in v2 is not forced to discovery.

### Task 7 — Tiered topic retrieval (R8, D2)

**Root cause:** `buildTopicOr` emits literal `ilike.%phrase%` per topic, so "Macau history" misses "Macao history and Chinese cultural heritage" while `topicScore` (word-boundary) would have matched. The dev paraphrase passed only because it typed "Chinese history", a real substring of the title. Retrieval and ranking disagree.

**Files:** `lib/assistant/discovery/topic-match.ts` (new), `lib/assistant/discovery/rank.ts`, `lib/assistant/data/discovery.ts`, `evals/assistant/discovery-fixture.ts`, `tests/assistant/discovery-rank.test.ts`, `tests/assistant/discovery-data.test.ts`, `tests/assistant/discovery-topic-match.test.ts` (new).

**Implementation**
1. `topic-match.ts` exports `normalizeTopic`, `topicVariants(topic)` (bounded: original, Macau/Macao swap, punctuation-normalised; ≤ 3), `significantWords(topic)` (≥ 4 chars, stopword list, ≤ 6), and `matchTopic(course, topics) => { tier, perTopic: { topic, tier, field }[], score }`.
2. Tier weights per D2; `score` normalised to 0..1 the same way `topicScore` is today (sum / topics.length, capped at 1).
3. `rank.ts:topicScore` delegates to `matchTopic(...).score`; the 0.20 topic weight and title-vs-body ratio are unchanged for tier 1.
4. `data/discovery.ts`: SQL prefilter = OR over phrase + variants + significant words, capped at `MAX_TOPIC_TERMS = 12`, still one `.or(...)` on the same builder. Relevance is decided in TypeScript by `matchTopic`, not by SQL.
5. Fallback: if fewer than `MIN_TOPIC_COURSES = 3` courses reach tier ≤ 2, tier-3 matches are admitted, `examined.topicFallback = true`, and a note says the topic match was broadened.
6. `examined` gains `topicTier: 1 | 2 | 3 | null`; `candidates[].matched` gains `"topic: <phrase>"` / `"topic words: <…>"` / `"topic keyword (broadened)"`.
7. Fixture `topicMatches` delegates to `matchTopic` so live and unit behaviour cannot drift.

**Precision and recall tests**

| Test | Expectation |
|---|---|
| `topics: ["Macao history"]` | GEGA1000 tier 1 (title/description phrase) |
| `topics: ["Macau history"]` | GEGA1000 retrieved via the variant → tier 1 |
| `topics: ["Chinese cultural heritage"]` | GEGA1000 tier 2 (all words present, noncontiguous) |
| `topics: ["Chinese history"]` | GEGA1000 (and GEGA1002 where its description matches) — no unrelated "Chinese" course promoted above them |
| Noncontiguous multiword (`"heritage Chinese Macao"`) | GEGA1000 still tier 2 |
| Generic keyword negative (`topics: ["Chinese"]`) | unrelated courses that merely contain the word rank below phrase/all-word hits; no precision cliff |
| Existing `"AI"` vs `"daily"` | unchanged (no substring match) |

### Task 8 — Compatibility scope and evidence fan-out guidance (R7, D4)

**Root cause A:** the model treats `required.noClash` and `mutualClashes` as combination proof. **Root cause B:** discovery hides its own `reviewTerms` enrichment, so the model reads reviews one course at a time (4–6 calls in 13 turns); follow-ups about mutual clashes re-derive per-section times (7–9 calls) because prior tool results are trimmed to 200 characters.

**Files:** `lib/assistant/discovery/discover.ts` (`DISCOVERY_NOTES`), `lib/assistant/discovery/tool.ts`, `lib/assistant/prompt.ts`, `tests/assistant/discovery.test.ts`, `tests/assistant/prompt.test.ts` (or existing prompt test).

**Changes**
1. `DISCOVERY_NOTES` gains: "`required.noClash` checks each section against the saved plan separately; two individually compatible sections can still clash — use the combination preview for that." and "`mutualClashes` covers only the returned best sections."
2. Tool description states the same, and names `preview_timetable` as the combined check.
3. Prompt bullet (shared with Task 6): "Whether several picks fit together needs `preview_timetable`, not individual fits"; and "when reviews matter, pass `reviewTerms` in the discovery call instead of reading each course's reviews."
4. No step-budget change; no new tool.

**Tests**
- `notes` contains the combined-fit distinction; a discovery result with `mutualClashes` cannot be described as combination-safe by the notes text.
- Prompt has exactly one bullet covering both combined-fit and `reviewTerms`.
- Unit: a discovery call with `reviewTerms` yields `reviewEvidence` for the top 3 (existing coverage extended), so the single-call path is demonstrably sufficient.

**Acceptance:** no claim in prompt/description/notes that re-running discovery proves mutual compatibility; `maxToolCalls` ceilings unchanged.

### Task 9 — Safe compaction and oversized stress test (R10, D8)

**Files:** `lib/assistant/discovery/discover.ts` (`shrinkDiscoverResult`), `lib/assistant/discovery/schema.ts` (`compaction.downgraded?`), `tests/assistant/discovery.test.ts`.

**Trim order (later stages only when still over budget)**

1. `reviewEvidence.excerpts` → 1, then 0.
2. `matched` / `tradeoffs` / `otherSections` → 1.
3. Titles, `otherSections`, `noListedSections`, `reviewEvidence`.
4. `ranking` (kept ≥ 80 chars).
5. Candidate count (never below 1).
6. `meetings` detail, `instructors` → 1.
7. **Never dropped:** `timetable.plannerVersion`/`status`/`planComplete`, `candidates[].fit`/`clashes`, `mutualClashes`, `notApplied`, `unverified`, `examined.truncated`, `compaction`.

**Safety-note rule:** the three safety-critical notes (individual-vs-combined fit, no official exam/prereq/seat data, suggestedYear is not eligibility) are trimmed only after everything else; the non-safety ratings note goes first. If the payload is still over budget, `candidates[].fit` values that depend on dropped evidence are downgraded (`verified_no_clash` → `incomplete`), `compaction.downgraded = true`, and a note records it.

**Test (> 12 000 chars fixture: 8 candidates, multi-meeting sections, `mutualClashes`, `unverified`, `notApplied`, all notes)**
- Serialised length ≤ `MAX_DISCOVERY_RESULT_CHARS`.
- `compaction.truncated === true`; `compaction.dropped` non-empty.
- `mutualClashes`, `unverified`, `notApplied`, `examined.truncated`, `timetable.plannerVersion`, every `candidates[].fit` present and unchanged **unless** `compaction.downgraded` is true, in which case no fit remains `verified_no_clash` while its supporting fields are absent.
- The three safety notes present; the ratings note may be absent.
- A second test at extreme size (> 60 000 chars input) asserts the same invariants and that at least one candidate survives.

**Acceptance:** no positive claim without its qualification; existing shrink tests still pass.
