## 1. Delivered

| Phase | Result |
|---|---|
| Quota semantics | One atomic claim per logical turn. Continuation runs and retries within 5 minutes reuse the charge; new turns charge. Both hour and day windows are checked before any write. Denials never call the runtime. Storage failures return 503 and never bypass the check. |
| Server enforcement | Seven `app_config.ai_*` columns override environment defaults; every value is clamped to code ceilings in `lib/assistant/limits.ts`. `maxSteps`, output tokens, timeout, turn cap, history, and both quotas are resolved per run. |
| Admin configuration | `POST /api/admin/app-config` validates bounded nullable values, requires a platform admin for numeric limits, and audits `before`/`after`. Access mode remains editable by any admin. |
| Usage visibility | `GET /api/admin/assistant/usage` returns aggregate counts, token totals, and optional cost estimates with `private, no-store`. No hashes, prompts, replies, or tool arguments. |
| Retention | `prune_assistant_telemetry()` deletes usage events >90 days, charges >30 days, rate-limit rows idle >7 days. The route triggers it fire-and-forget at most once per 6 hours per isolate. |
| Student UX | Quota, execution-limit, provider balance/auth/rate-limit/timeout, and 503 copy are distinct fixed strings. Provider text is never echoed. |
| Admin UI | `/admin/assistant` composes the existing access panel, a platform-only limit editor with min/max/inherit, and a usage panel with measured vs estimated labels and a refresh action. |

## 2. Accounting contract implemented

- `claim_assistant_turn` takes a per-user advisory transaction lock, checks the recent-turn ledger, evaluates hour then day, and only then upserts both counters and the charge row plus an `accepted` event.
- `turnKey = sha256(userHash \0 threadId \0 latest-user-message-id-or-content-hash)`. CopilotKit `runId` is not used because it changes for continuation runs.
- 409 (conversation limit) and 413 (prepared payload) occur before the claim and are recorded as `rejected`.
- Provider failures and client cancellations remain charged, matching the documented existing policy; no refund path was added.
- Preview workers (`PREVIEW_DB_READONLY=1`) use the in-memory claim and never write usage.

## 4. Limitations reported

1. **Browser acceptance not performed.** The admin page needs Clerk and Supabase credentials; the local environment has neither, so the panel was verified through jsdom component tests and the page through its server-render test. Student chat regressions were covered by the seven integration suites driving the real route and runtime.
2. **Concurrency validated statically.** No local Supabase instance was available for an opt-in concurrency test. The advisory-lock and check-before-write ordering are asserted by the SQL contract test.
3. **Cost is an estimate.** It is `null` unless `AI_PRICE_INPUT_PER_MTOK` and `AI_PRICE_OUTPUT_PER_MTOK` are set; cached input uses `AI_PRICE_CACHED_INPUT_PER_MTOK` when present. No billing claim is made.
4. **Audit-log retention is deferred.** Deleting `admin_audit_log` rows requires product/compliance approval and is documented in the spec.
5. **Totals are 14-day aggregates.** `assistant_usage_daily(14)` bounds the table and totals; older data remains available only at the database level until the 90-day prune.
6. **No durable conversations.** Chat history remains in-memory and client-supplied; no retention setting was added.

## 5. Scope guardrails

- V2 was not merged into `dev` or `main`; the branch is based on the verified `feat/global-assistant-v2` tip.

## 6. Post-merge fix — local schema drift

**Symptom:** `/admin/assistant` logged `[assistant-settings] limit read failed: column app_config.ai_quota_per_hour does not exist` and limit controls silently used environment defaults.

**Cause:** the running local database was bootstrapped before this migration existed, and the bootstrap path imports `supabase/schema.sql` without replaying migrations. The snapshot was itself incomplete: it mentioned the three new RPCs only in a comment and never included `request_rate_limits` / `consume_rate_limit`, so a fresh bootstrap would reproduce the failure.

**Fix:**

- Applied `20261028_assistant_admin_ops.sql` to the local Supabase stack.
- Inlined `request_rate_limits`, `consume_rate_limit`, `claim_assistant_turn`, `assistant_usage_daily`, and `prune_assistant_telemetry` (with grants) into `supabase/schema.sql`.
- Removed the PostgreSQL 17-only `SET transaction_timeout` and made `CREATE SCHEMA public` idempotent so `scripts/bootstrap-local-db.sh` (`ON_ERROR_STOP=1`) completes on the pinned PG15 stack.
- Added snapshot regression assertions in `tests/database/assistant-ops-sql.test.ts`.

**Evidence:** a scratch database bootstrapped cleanly from `schema.sql` + `seed.sql` with `ON_ERROR_STOP=1`; `claim_assistant_turn` charged a first turn, reused the charge for a continuation, and denied the third turn beyond a 2/hour limit; `assistant_usage_daily(14)` returned 14 rows; `consume_rate_limit` returned its window. `tests/database` passed 43/43, `tsc --noEmit` exit 0, `lint` exit 0.

No application code change was required; the API and route already failed closed on quota storage errors.
