## A. What shipped

V2.1 adds rich tool rendering and local catalog filtering on top of the V2.0 assistant stack:

- **Course detail card** — `get_course` results render as a structured course detail card (`CourseDetailToolResult`), with offered badge, instructors, and sparse-field handling.
- **Section cards** — `get_course_sections` results render as per-section cards with meeting rows (`CourseSectionsToolResult`).
- **Local All / Offered filter** — catalog search result blocks expose **All** and **Offered only** toggles that filter the **loaded** rows in the UI without a new model turn.
- **`filter_catalog_results` frontend tool** — the agent can re-filter a prior search by `resultSetId` (`offered` | `all`), with scope text when results are paginated.
- **Prompt rules 3 and 15–17** (`lib/assistant/prompt.ts`) — ground answers in tool/context data (rule 3); card-aware brevity for search, course, and section tools (15); contextual referents and `filter_catalog_results` instead of re-search (16); `get_course` then `get_course_sections` for schedule questions, with a cap on offered instructors (17). Unit checks in `tests/assistant/agent.test.ts`.

Supporting pieces: bounded catalog result-set collection and context summary (`lib/assistant/catalog-result-sets.ts`, `useCatalogResultsTool`), filter tool render, and the scripted V2.1 integration suite.

- **Runner follow-up runs** — `InMemoryAgentRunner` `maxRunsPerThread` was raised from 1 to 8 so a `filter_catalog_results` tool with `followUp` can keep its follow-up run; `ASSISTANT_MAX_STEPS` stays 5 and the runner's `maxBytes` stays 2MB.

## E. Known limitations

- The section schema has no lecture/tutorial type or semester field, and there is no per-section instructor on the section rows—only course-level instructor context from the preceding `get_course` flow.
- Filtering applies only to courses already loaded in the chat card for that result set; `search_catalog` has no offered-only query parameter, so finding every offered match across the full catalog still requires paging through search.
- Choosing which result set the student means with phrases like “those” is model behaviour guided by the catalog-results context and prompt rule 16, not deterministic application code.
- Older tool results are truncated to about 200 characters server-side in `lib/assistant/conversation.ts`, so for earlier turns the model relies on the bounded context summary rather than full JSON payloads.

### H.1 Finding A — Filtered result ordinal references

| Field | Assessment |
|---|---|
| **Report** | After MATH search (10 loaded rows; only APAC1000 and ECON1002 offered), user selects **Offered only** manually, asks about “the second course”; assistant answers with APAC2000 (2nd row under **All**, not 2nd visible under **Offered only**). |
| **Reproduction evidence** | **Partial in repo; high-confidence logic repro.** `tests/components/assistant-v2-1.integration.test.tsx` proves manual **Offered only** updates the card UI and `store.filters`, and that the next agent run receives catalog context (filter follow-up path). It does **not** assert ordinals after a manual filter or call `get_course` for “the second course.” Unit test `tests/assistant/catalog-result-sets.test.ts` (`summarizeCatalogResultSets`, filter `c4: "offered"`) locks in the bug shape: `courses[1]` is `{ position: 2, courseCode: "MATH1002", isOffered: true }` while `applyCatalogFilter(..., "offered")` order is `MATH1002` then `MATH1005` — so **position 2 in context is the 1st offered row, not the 2nd visible row.** Mapping the user’s APAC/ECON example: 2nd loaded = APAC2000; 2nd **visible offered** = ECON1002. |
| **Confidence** | **P1 confirmed in architecture** (ordinal semantics contradict filtered UI). **User-specific APAC2000 outcome: high** given that code path; not re-run in a live signed-in browser in this pass (§D still unverified). |
| **Root cause** | Manual filter **does** reach the model: `CatalogFilterProvider` → `useCatalogFilter` / `setFilter` in `search-catalog-tool-render.tsx` and the same store in `use-catalog-results-tool.tsx` (`contextValue` memo deps include `store?.filters`). The defect is **not** stale filter state; it is **position indexing**. `summarizeCatalogResultSets` always emits `position: courseIndex + 1` over the **full loaded** list while also emitting `filter: "offered" \| "all"`. The UI renders `applyCatalogFilter` order (`displayedCourses`). Prompt rule 16 says “Take positions and course codes from the context only” but never states that positions are **unfiltered load order**. `shownCourseCodes` exists only on `filter_catalog_results` **tool results**, not in the standing catalog context blob. Resolution is **model + ambiguous context**, not a deterministic frontend resolver. |
| **Data flow (manual filter → tool)** | User clicks **Offered only** → `useCatalogFilter(resultSetId).setFilter("offered")` → React re-render hides non-offered cards → `useCatalogResultsTool` recomputes `summarizeCatalogResultSets(collectCatalogResultSets(messages), filters)` → CopilotKit sends updated context on the **next** `/api/copilotkit` run. No run on click (asserted in integration test). User asks “second course” → model reads context → chooses `courseCode` (often position 2 in **load** order) → server `get_course` executes whatever code the model passes; **no validation** against visible/filtered ordering. |
| **Source of truth today** | **UI:** filtered visible order. **Agent context `position`:** original search load order. **Winner for ordinals:** load order unless the model inferentially maps “second” to offered-only (unreliable). |
| **Smallest correction** | In `summarizeCatalogResultSets` (`lib/assistant/catalog-result-sets.ts` ~203–220): when `filter === "offered"`, emit courses from `applyCatalogFilter` with `position` renumbered 1…n (and optionally retain `loadedPosition` for disambiguation). Align prompt rule 16 with that schema. Optional: include `shownCourseCodes` in context whenever filter ≠ `all`. |
| **Tests to add** | (1) Unit: offered filter summary positions match `applyCatalogFilter` order. (2) Integration: after manual **Offered only**, scripted model call asserts catalog JSON positions and `get_course` code for “the second course” equals 2nd **visible** code. (3) Browser regression: same flow on authenticated localhost per §D scenario C + new ordinal scenario. |

### H.3 Recommended context-resolution contract (deterministic, bounded)

Use a **priority stack** (first match wins; if two rules conflict at same priority, one clarification question):

1. **Explicit identifier** in the latest user message (course code, instructor name matching tool rules) → use it.
2. **Ordinal / “first|second|third”** in the latest message → refer to the **newest** catalog `resultSetId` unless the user names another set; positions taken from **visible rows** after the active `filter` (post–H.1 fix).
3. **Deictic “this course|this instructor|this page”** → if page context contains `courseCode` or `instructor`, use it; if page is `other` or wrong kind, ask once.
4. **Anaphora “that one|the one we discussed|it”** (no explicit code) → most recent **explicit** course/instructor code from user or tool results in the kept conversation window; if page context disagrees with “this” wording, prefer page for “this” and chat for “that”.
5. **Never** use Markdown the model invented earlier as authority; cards and context JSON beat prose.

This is **not** “page always wins”; e.g. “Compare this course with CISC2001” on a course page should keep “this” from the page and CISC2001 from the message.

### H.5 Acceptance criterion (addendum)

The assistant must act on **correct current application state**: filtered visible ordering for list referents, and URL-backed page for “this course,” with explicit codes and bounded chat anaphora — not whichever course code appeared most recently in prose or unfiltered position indices.
