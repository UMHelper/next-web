This note covers the **text-first** presentation plan. Stacked course or instructor comparison widgets were **not** shipped.

## 1. Features delivered

V2.2 on this branch adds adaptive, text-first presentation for one user turn:

- **Text-first default.** If `present_response` is omitted, rejected, or accepts `show: []`, the sidebar stays prose/Markdown only. Existing course and section cards do **not** auto-mount from successful `get_course` / `get_course_sections` calls.
- **Opt-in course and section cards.** Accepted `present_response.show` entries use closed components `course_detail` and `course_sections` (one to three course codes, deduped). Cards mount only when the model opts in during the same user turn as the lookups.
- **Markdown comparisons.** Course and instructor comparisons are answered in prose or a short Markdown table (prompt rule 11). There is no comparison widget or stacked comparison layout.
- **Recommendation prompt.** After facts, the model puts its recommendation on its own line starting with `Suggestion:` (rule 11).
- **Discussed-course follow-ups.** Courses retrieved in the chat are summarized in context; ordinals can bind to discussed courses when that list is newer than the last catalog search (see §5).

## 2. Architecture

`present_response` is a server tool in the **same user turn** as academic lookups. A later model step in that turn is valid. `ASSISTANT_MAX_STEPS` is still 5.

`executePresentResponse` accepts only `{ show: PresentShow[] }` where each item is `{ component: "course_detail" | "course_sections", course: "<CODE>" }`. Omitted `show`, empty `show`, invalid payloads, or duplicate/conflicting entries reject or yield no cards; the UI remains text-first.

Rich blocks come from `planRichBlocks`: an accepted `show` entry must match a same-turn `get_course` or `get_course_sections` call (by component and course code on the call arguments, and on the parsed result when present). `planRichBlocks` may enqueue a claimed course or section block from that call’s arguments before the tool result string exists, so a card can mount as the lookup finishes. Only those matched calls render `CourseDetailToolResult` or `CourseSectionsToolResult`; there is no card without a corresponding lookup in the turn. Agent Activity uses `callsForActivity`, which **drops** `present_response` from the trace while still showing real lookups.

There are **no** `course_comparison`, `instructor_comparison`, or dedicated comparison UI modules in this delivery.

## 4. Academic correctness

Comparisons and instructor answers are grounded in parsed tool JSON, not model prose inventing fields.

- **Score scales** are `RATING_SCALES` in `lib/assistant/rating-semantics.ts`: Overall (`result`: 1 Never!, 5 Completely.), Reported grade (`grade`: 1 is F, 5 is A; higher means higher grades reported), Difficulty (`difficulty`: 1 Very hard, 5 Very easy), Usefulness (`reward`: 1 Waste of time, 5 Very useful), Attendance checks (`attendance`: 1 Always, 5 Never.).
- **Review counts** come from `commentCount` on course rows in tool payloads. Prompt rule 11 asks the model to cite counts when comparing instructors; integration tests assert count copy in Markdown answers (`tests/components/assistant-v2-2.integration.test.tsx`).
- **No review bodies in comparison context.** `get_course_reviews` is not used to build a comparison; review text is for explicit review questions only.
- **Distinct codes** across follow-up turns and page-vs-named-code binding are covered in `tests/assistant/course-referent.test.ts` and the V2.2 integration suite.

## 5. Context

- **`kind: "multiple"`** — `bindCourseToolArgs` passes through each explicit code the student named; it does not rewrite one named code onto another. `pageCourseCode` applies only to “this course” style referents, not to replacing a written code.
- **Discussed courses** — `discussed-courses.ts` builds a bounded context list (newest turn first). When `active.newerThanCatalog` is true, ordinal referents with a discussed-courses `resultSetId` resolve to `"the first one"` / `"the second one"` in **discussed** order, not the catalog list.
- **Ambiguous dual ordinals** — “Compare the first and the second” in a catalog list remains the V2.1 ambiguous ask; this plan binds a **single** ordinal to discussed courses, not two catalog ordinals at once.

## 8. Limitations

- If the model omits `present_response` on “tell me more” or “show details”, the student gets text and activity only—no card until they ask again with explicit inspect language.
- If the model wrongly requests `course_detail` for “What is CISC2001?”, a card will appear. There is no client-side keyword override; live eval (when run with `AI_API_KEY`) measures that rate.
- “Compare the first and the second” in a catalog list stays the V2.1 ambiguous ask.
- `get_course_reviews` is not fetched for comparisons; aggregate scores and `commentCount` on course/instructor payloads are the evidence.
- Attendance remains in `RATING_SCALES` because it is in the schema; the submit control for it stays hidden in forms.
- `ASSISTANT_MAX_STEPS` is still 5; a presentation step consumes one step.
- Live DeepSeek presentation remains **model-gated**; the tuning pass hit 39/39 on the fixed benchmark but variance may return on new phrasing — holdout set is informational only.
- Several §7 browser scenarios remain **unverified** in browser (sections, compare, catalog filter, ordinals); covered by `tests/components/assistant-v2-2.integration.test.tsx`.
